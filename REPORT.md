# REPORT — Food Security Early Warning Agent

## 1. Problem statement

**User:** a food-security/humanitarian analyst at an NGO or a regional early-warning
unit (e.g. a FEWS NET or CEMAC-region food-security desk analyst) who needs to
quickly assess acute food-insecurity risk for a specific region, cross-check
whether a claim is corroborated across independent reports, and get an
objective climate signal — without manually re-reading dozens of country
outlook reports each time a new question comes in.

**What the agent does that a chatbot or search engine cannot:** a generic
chatbot would answer from parametric knowledge with no grounding and no way to
verify corroboration; a search engine returns documents, not a synthesized,
confidence-scored answer. This agent (1) retrieves the specific relevant
passages via hybrid search + reranking, (2) explicitly checks how many
independent sources corroborate a claim before answering, (3) pulls a live,
independent climate signal (NASA POWER) to cross-check report-based claims
against objective data, and (4) forces every answer through a critic pass
that rejects unsupported conclusions.

**Concrete scenario:** an analyst asks *"Is Niger's Tillabéry region at risk
of deteriorating past Crisis level this outlook period?"* Instead of
re-reading the full Niger outlook report, the agent retrieves the relevant
passages, cross-references the claim against the corpus, and returns a
structured EVIDENCE/ANALYSIS/CONCLUSION/CONFIDENCE answer in seconds — a task
that would otherwise take the analyst 15-30 minutes of manual document review.

## 2. Architecture

See `docs/architecture.md` for the full diagram. In summary: user question →
L1 input filter → analyst step (MCP tool calls: hybrid-search retrieval,
corroboration check, optional live climate data) → few-shot CoT synthesis
with Self-Consistency (k=3) → critic agent (second LLM role, APPROVE/REJECT)
→ final answer. Every LLM and tool call is wrapped in a Langfuse span.

**One non-obvious design decision:** L1 input filtering is applied not only
to the user's question but a second time to every string returned by a tool
call, before it enters the evidence context. Trade-off: a small extra regex
pass per tool call, in exchange for closing an indirect prompt-injection
attack surface — a poisoned document in the retrieval corpus could otherwise
inject instructions the user never typed. See `docs/architecture.md` for the
full reasoning.

## 3. Evaluation

Metrics generated by running `python src/eval_ragas.py` and
`python src/cost_latency.py --runs 10` with a real `MISTRAL_API_KEY` (the
`ragas` package failed to import due to a `langchain_community` dependency
conflict in our environment, so these numbers come from the script's
fallback manual metric implementation — a lexical-overlap proxy for the
four RAGAS metrics, not the LLM-judge-based official RAGAS computation;
see `src/eval_ragas.py::score_fallback` for the exact method).

| Metric | Baseline (BM25 top-k only) | Final (hybrid + rerank) | Technique that caused the change |
|--------|---------|-------|----------------------------------|
| context_recall | 0.571 | **0.708** | Dense retrieval + RRF fusion recovers relevant passages BM25 alone misses (paraphrased/semantic matches) |
| context_precision | 0.097 | **0.125** | Cross-encoder reranking demotes lexically-matched-but-irrelevant passages surfaced by BM25/RRF |
| faithfulness | 0.728 | 0.729 | Essentially unchanged — faithfulness depends mainly on the synthesis prompt (few-shot CoT grounding), not on which passages were retrieved |
| answer_relevancy | 0.771 | 0.748 | Essentially unchanged (slightly lower) — with only 3 retrieved passages either way, the answer's topical relevance to the question is set more by the synthesis step than by retrieval quality; this fallback metric is also a coarse word-overlap proxy, not the real RAGAS embedding-similarity computation |

Both recall and precision improve with hybrid retrieval + reranking, as
expected: BM25-only retrieval misses semantically-related-but-lexically-
different passages, and without reranking, some BM25/RRF-surfaced passages
are only superficially related. Faithfulness and answer_relevancy stay flat
because they are driven mainly by the synthesis prompt design rather than
which top-3 passages were retrieved — with a small, focused corpus (8
documents), most retrieval variants surface passages faithful/relevant
enough that the synthesis step is the bottleneck, not retrieval.

Average run cost (USD): **$0.0002** per run (estimate; see caveat in

Average latency (seconds): **22.3s** per run (includes 3 Self-Consistency
synthesis calls + 1 critic call + 2 tool calls, all sequential)
Tool call distribution (10 runs): `search_food_security_reports`: 10/10,
`cross_reference_claim`: 10/10 (both tools called on every run, as designed)
TokenBudget triggered: No (not triggered in these 10 runs — the 60,000-token

## 4. Security

5/5 injection tests pass (verified in this environment — see
`tests/test_security.py`, run via `python -m pytest tests/test_security.py -v`):

1. Direct instruction-override ("ignore all previous instructions...") — blocked by L1
2. Role impersonation / jailbreak framing ("act as DAN, do anything now") — blocked by L1
3. Fake role-tag injection (`</user><system>...`) — blocked by L1
4. Unicode homoglyph evasion (full-width character trick) — blocked by L1 after NFKC normalization
5. Legitimate query — correctly passes (no false positive)

Plus 4 bonus tests on the L4 gate and TokenBudget (unknown-tool fail-closed,
known-tool allow, per-tool call cap enforcement, budget-exceeded exception).

**One real injection attempt blocked, and which layer caught it:** the
unicode-homoglyph test (`\uff29\uff47\uff4e\uff4f\uff52\uff45 previous
instructions...`, full-width Unicode variant of "Ignore") is caught
specifically by L1's NFKC normalization step, which collapses the full-width
characters to their ASCII equivalents before pattern matching — without that
normalization step, the raw regex would miss this payload entirely, since the
literal Unicode code points don't match the ASCII pattern. This is the layer
doing genuine work, not the pattern list itself.

## 5. EU AI Act assessment

**Risk tier: Limited risk** (not high-risk). The agent does not fall under
any Annex III high-risk category as currently scoped: it does not determine
an individual's eligibility for essential public/private services or
benefits, does not perform biometric identification, and is not used in
employment, law-enforcement, migration/asylum, or justice-administration
decisions. It is a research/analysis support tool for humanitarian analysts —
the analyst remains the decision-maker.

**Caveat:** if this agent's output were ever wired directly into an
operational aid-allocation decision (e.g. automatically flagging which
regions receive food assistance without human review), it would move toward
the Annex III "access to essential private services and public services and
benefits" high-risk category, given the population-level consequences of
such decisions.

**Obligation from the Limited risk tier:** Article 50 transparency — users
must be able to tell they are interacting with an AI system and that its
output should not be treated as a verified, official assessment.
**Implementation:** every answer is returned with an explicit CONFIDENCE tag
and the underlying EVIDENCE section, so the analyst can see exactly what the
conclusion is (and isn't) grounded in, plus the critic agent's
APPROVE/REJECT verdict — this makes the AI-generated, non-authoritative
nature of the output visible rather than presenting it as a verified fact.

## 6. Limitations & what's next

**What would break first in production:**
1. **Corpus staleness** — the retrieval corpus is currently 8 synthetic
   documents; in production this needs a real, continuously-updated ingestion
   pipeline from FEWS NET/FAO GIEWS, or the agent will confidently answer from
   an outdated snapshot. This would manifest as soon as the agent is asked
   about a region or timeframe not covered by the last ingestion run.
2. **Self-Consistency majority-vote is a coarse string-normalization match**
   (see `reasoning.py::_normalize_conclusion_for_voting`) — two semantically
   identical conclusions phrased differently would be treated as disagreeing
   samples, artificially lowering the reported agreement score. This would
   surface most on ambiguous, open-ended questions where the model has more
   phrasing freedom.

**Next sprint:**
- Replace the majority-vote string match in `reasoning.py` with an embedding-
  based clustering of the 3 sampled conclusions (cosine similarity threshold)
  instead of exact-normalized-string matching.
- Add a real token-accounting hook to `call_llm` (reading `resp.usage` from
  the Mistral response) instead of the current rough character-length proxy
  used for `TokenBudget`, to get an exact rather than estimated cost figure.
- Add a scheduled ingestion job to refresh `data/corpus/` from FEWS NET/FAO
  automatically, with a source-freshness check surfaced to the analyst.
